# 员工端 v0.5.1 修复、打包与验收

更新日期：2026-09-09

状态：测试通过，源码已提交、打 `v0.5.1` 标签并推送到 GitHub

## 1. 本轮结论

第三轮公司内网多终端实机测试已完成并通过。测试中发现企业端下发资料时，如果资料名称已经带 `.md`，员工端仍会追加扩展名，最终产生 `.md.md` 文件。

该问题已同时在员工端和企业端修复，并将员工端版本提升为 `0.5.1`。新的 ZIP 与 EXE 已生成，ZIP 已从空白目录完成真实启动、浏览器页面、在线下发、离线队列、重启恢复和删除清理回归；EXE 已完成压缩包完整性与关键文件哈希校验。

本问题属于文件名规范化和本地物化逻辑，不需要再次组织物理跨设备测试。网络、心跳、在线下发、离线队列和中枢重启链路已经由 P2、P3 实机测试覆盖；本轮重点验证修复后的文件名在同一协议链路中表现正确。

## 2. 问题发现与修复

### 2.1 实机发现

第三轮环境：

- 企业中枢：`192.168.11.55:3099`，企业端 `0.2.1`；
- 员工端 C：`192.168.11.15:3080`，Windows，员工端 `0.5.0`；
- 员工端使用 `kaiwu-praxis-setup-v0.5.0.exe` 安装；
- 在线下发内容、UTF-8 编码和 SHA-256 均正确，但实际文件名为 `第三轮公司内网实机验收资料.md.md`。

随后用不带扩展名的资料名称重新下发，实机链路恢复正常。P3 其余在线、离线、重启和清理项目均通过。

正式证据见：[第三轮公司内网多终端实机测试验收报告](../../测试报告/P3-公司内网多终端测试/第三轮公司内网多终端实机测试验收报告.md)。

### 2.2 代码修复

员工端 `lib/admin.mjs`：

- 新增并导出 `materializedDocFileName`；
- 对扩展名进行大小写不敏感判断；
- 名称没有 `.md` 时追加一次；已有 `.md` 或 `.MD` 时保持原样。

企业端 `lib/enterprise-hub.mjs`：

- 新增 `normalizeBatchPayload`；
- 对新增/删除资料和 SOP 的名称统一去除末尾 `.md`；
- 对规范化后的空名称继续执行参数校验；
- 避免旧员工端或不同调用入口收到带重复扩展名风险的负载。

测试补充：

- 员工端新增 `scripts/test-document-filenames.mjs`，6 个文件名用例通过；
- 企业端 `scripts/test-hub.mjs` 扩展到 20 项检查并通过。

离线 tarball 是本机交付包的可复现来源；源码同时通过不可变的 GitHub `v0.5.1` 标签发布。后续重建交付包时，可继续使用从该标签生成并校验哈希的内置 tarball。

## 5. 接手后的发布动作

1. 从 GitHub `v0.5.1` 的空白 profile 安装一次，确认标签内容与本机交付包一致。
2. 从 GitHub `v0.2.1` 的空白 profile 安装企业端并完成健康检查。
3. 若正式交付 EXE，补做一次 SFX 图形化双击、解压、启动和首页检查。
4. 仓库转移后更新安装 URL、remote 和便携包来源，再做一次空白安装。
5. 发布前复核 `SHA256SUMS.txt`；如果重新打包，旧哈希全部作废，必须重新记录。
